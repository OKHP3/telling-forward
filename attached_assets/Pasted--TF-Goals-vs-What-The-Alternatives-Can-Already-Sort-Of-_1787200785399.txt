# TF Goals vs. What The Alternatives Can Already (Sort Of) Do

Reframing the question: strip away "which platform is TF's competitor" and ask instead "which platform, bent hard enough, could already deliver a piece of what TF wants." Different answer. Three platforms come up as real partial-fits. The other three (Medium, Substack-as-collaboration, standalone Patreon) don't clear the bar for any TF goal on their own merits, only as bolt-on monetization plumbing.

| TF Goal | Best Partial-Fit | Why It's Partial, Not Full |
|---|---|---|
| Governed co-creation (steward accepts/rejects into canon) | **GitHub** | Fork/PR model already does gated contribution. Missing: narrative-specific review states, plain-language framing |
| Non-linear worldbuilding capture (capsules) | **GitHub** | Issues + Projects v2 already model discrete non-linear objects with custom fields. Missing: enforced taxonomy, prose UX |
| Immutable provenance / attribution ledger | **GitHub** | Commit history + git blame is already an immutable ledger. Missing: human-readable narrative framing |
| Reader clarity: canon vs. alternate vs. experimental | **AO3** | Tag-wrangling system is the best canonical-vs-variant signal system that exists in fiction publishing, full stop | Missing: prospective co-creation, originator governance |
| Consent/withdrawal/archive lifecycle for a contribution | **AO3** | Orphaning + content-warning taxonomy is the closest existing consent pattern. Missing: applies to content rating, not AI-derivative consent |
| Extensibility / bring-your-own-tooling | **GitHub** | Apps + Actions is a mature third-party extension model. Missing: none of it is AI-model-aware |
| Notification model (contributor status changes) | **GitHub** | Native watch/mention/review-requested covers most of it. Missing: plain-language narrative framing (ADR-0002) |
| Eventual monetization of a governed universe | **Patreon / Substack** | Membership-gating and subscription billing already solved. Missing: neither has any concept of a "world" as the billable unit, only a creator |
| Voice-first natural-language contribution | **None** | Genuine whitespace. No competitor touches this |
| Per-action AI-derivative consent (CIE/PIE) | **None cleanly** | AO3's content-warning enum is the closest analog, and it's not close |

Two real gaps nobody's solved: voice-first capture, and per-action AI-derivative consent. Everything else has a decent donor organ somewhere in the market. That's the actual finding here, and it changes the ADR-0003 conversation: TF isn't inventing a new substrate, it's assembling parts that already exist and bolting on the two pieces nobody has.

Given that, here's the reverse-engineering spec on the two strongest donors, written the way you'd write it if you were about to fork and extend rather than compete.

---

# Spec 1: GitHub, Reverse-Engineered (Primary Donor)

This is the one that matters most, because TF's own architecture already describes itself in GitHub's vocabulary: storyworld = repo, path = branch, contribution = commit, proposal = PR, capsule = Issue. TF isn't competing with GitHub. TF is currently *rebuilding a worse version of GitHub in Postgres* while sitting on top of the real thing. That's the finding ADR-0003 needs to reckon with.

## A. Core Object Model (Confirmed, Publicly Documented)

```
Git layer (content-addressed, immutable):
  blob   → file contents
  tree   → directory snapshot (pointers to blobs/trees)
  commit → snapshot pointer + parent(s) + author + message
  ref    → mutable pointer to a commit (branch, tag)

GitHub metadata layer (mutable, API-managed, NOT in git):
  Issue        → title, body, labels, assignees, state (open/closed), comments
  Pull Request → ref-to-ref diff + review state + merge state + linked Issues
  Review       → APPROVED | CHANGES_REQUESTED | COMMENTED | PENDING
  Label        → arbitrary tag, org-scoped, colorable
  Milestone    → grouping + due date
  Project (v2) → GraphQL-native board with custom typed FIELDS (not just columns)
  Discussion   → threaded, categorized, non-code conversation
```

The critical fact TF's schema is missing: **Projects v2 fields are typed and custom.** You can define a field called `Canon Status` with enum values `draft / submitted / under-review / returned-with-notes / accepted-into-canon / published-alternate` directly on a GitHub Project, no database required. TF's six-state proposal workflow already exists as a schema-less config away from being native GitHub, not a build item.

## B. Permission Model (Confirmed)

```
Org roles:        owner, member, billing-manager
Repo roles:        read, triage, write, maintain, admin
Team-based access: nested teams, CODEOWNERS-gated required review
Branch protection: required reviews, required status checks, required
                    signed commits, restrict-who-can-push
```

`CODEOWNERS` is the steward-governance primitive TF is trying to reinvent with a `stewards` table. A `CODEOWNERS` file mapping `capsules/*` and `paths/*` to a steward's GitHub handle already gates merge authority per-directory, natively, no custom auth layer.

## C. Contribution Workflow (Confirmed)

```
fork → branch → commit(s) → PR opened → review requested →
  { APPROVED → merge } | { CHANGES_REQUESTED → iterate } | { closed, unmerged }
```

Native states: 3 PR states × 4 review states = enough combinatorial surface to express 5 of TF's 6 states without any custom backend. The one state native GitHub genuinely can't express is `published-alternate` (accepted, but as a divergent canon rather than merged into main) — that's a **long-lived branch with protected status and a Pages build pointed at it**, not a missing feature, just an unconventional branch-protection config.

## D. Automation Layer (Confirmed)

```
.github/workflows/*.yml → triggered by webhook events
  (issues.opened, pull_request.review_requested, push, schedule)
→ runs in an isolated runner (GitHub-hosted or self-hosted)
→ can call GitHub API, external APIs, write commits, post comments,
  set required status checks
```

This is the state-machine engine TF needs and doesn't have. Every "business logic stub" currently sitting in the Express server (promote/disrupt/invert capsule logic) is an Actions workflow away from existing without a server process running at all.

## E. API Surface (Confirmed)

```
REST v3       — resource-oriented, stable, well-documented
GraphQL v4    — required for Projects v2 field manipulation
Webhooks      — event-driven, HMAC-signed
GitHub Apps   — installation-scoped tokens, fine-grained permission sets,
                short-lived (1hr), audit-logged, no PAT rotation problem
OAuth Apps    — user-scoped, broader, no installation concept
```

This directly resolves TF's open question 15.6. The repo is currently PAT-based (`GITHUB_PAT` secret, one long-lived token, no per-action audit trail). A GitHub App with scoped permissions (`issues:write`, `pull_requests:write`, `contents:read`, explicitly *not* `admin:org`) is strictly safer, gives per-installation revocability, and is the documented, supported pattern for exactly this use case. There's no version of this decision where PAT wins on merits; it's currently just easier to have already built.

## F. Infra (Publicly Documented via GitHub Engineering blog, not independently verified here)

```
Git storage:  Spokes — GitHub's own distributed, replicated git storage
Metadata DB:  MySQL, sharded via Vitess
Search:       Elasticsearch
Cache/queue:  Redis
```

Not actionable for TF directly (you're a consumer of the API, not the infra), but relevant context: GitHub's own war story is "we outgrew a single relational store for a graph-shaped problem and had to shard hard." TF is about to relearn that lesson at 1/100,000th the scale, prematurely, with a `provenance_records` table doing the same job git commit trailers already do for free.

## The Improvement Spec: What TF Bolts Onto GitHub, Using Its Own Lessons Learned

| TF Component | Currently Built As | Should Be |
|---|---|---|
| Auth to GitHub | PAT via `git-askpass.sh` | GitHub App, scoped permissions, installation tokens |
| Six-state proposal workflow | Would need custom Postgres enum + API | Projects v2 custom field (`Canon Status`), driven by an Action state machine on PR review events |
| Provenance ledger | `provenance_records` table | Commit trailers (`Provenance-Steward:`, `Contribution-SHA:`) + an Action that appends to an append-only `PROVENANCE.md` on every merge to `canon` |
| Capsule taxonomy enforcement | Manual label discipline | Action that validates `capsule:*` labels on Issue creation, rejects malformed ones via required status check |
| Steward authority | `stewards` table | `CODEOWNERS` mapped to GitHub team membership, enforced by branch protection |
| Reader-facing canon view | New frontend app (`artifacts/reader`) | GitHub Pages built by Action on every merge to `canon`, or a thin static site pointed at the Pages output |
| Notifications | Not built (ADR-0002 open) | Native watch/mention/review-requested covers ~70%; thin webhook-to-email layer for plain-language framing covers the rest |
| Voice ingestion | Writes to Postgres via API server | Whisper transcript → posted directly as an Issue comment via the App's `issues:write` scope, no DB row |
| Consent for CIE/PIE derivative work | Not designed | **Genuinely new.** Required PR template checkbox + required status check (`consent-verified`) that blocks merge without a signed consent trailer. GitHub has zero native concept of this — it's the one place TF has to build real infrastructure, not borrow it |

**What this buys, concretely:** it collapses ADR-0003 from "which architecture" to "how thin a layer on top of GitHub," which is a much smaller, much cheaper decision. It also quietly resolves open questions 15.1, 15.2, 15.3, and 15.6 as side effects, because the repo-per-storyworld question, the frontend-of-record question, and the auth question all have GitHub-native answers once you stop treating GitHub as a sync target and start treating it as the database.

# Spec 2: AO3 / otwarchive, Reverse-Engineered (Secondary Donor)

AO3 runs on **otwarchive**, an open-source Ruby on Rails application maintained by the Organization for Transformative Works. This is publicly documented (the codebase itself is open source), not inferred.

## Core Subsystems Worth Stealing

**Tag wrangling pipeline** — the single best implementation of "reader clarity about canonicity" that exists anywhere in fiction publishing:

```
Contributor enters freeform tag ("Alt-verse where Kaelen lives")
  → Volunteer tag wrangler reviews
  → Maps freeform tag to a canonical tag (or creates one)
  → Canonical tag attaches to a metatag hierarchy
  → Reader-facing filter uses canonical tags, never raw freeform input
```

This is exactly the pattern TF's capsule/story-path taxonomy is missing. TF currently relies on discipline (contributors correctly labeling `capsule:character`) with no wrangling layer to catch and canonicalize drift. AO3 solved this at a scale of tens of millions of tags with volunteer labor and a two-tier freeform/canonical model. TF should copy the *pattern*, not the volunteer-labor model — a steward-reviewed wrangling queue is a smaller version of the same idea.

**Rating and warning taxonomy** — fixed enum, not freeform:

```
Rating:   General / Teen / Mature / Explicit / Not Rated
Warnings: Choose Not To Use Archive Warnings / No Archive Warnings Apply /
          Graphic Violence / Major Character Death / Rape/Non-Con / Underage
```

This is the closest existing analog to a consent taxonomy, and it's the right shape for the gap TF actually has open (per-action CIE/PIE consent): a **fixed, small, enumerable set of consent states**, not a freeform text field, with an explicit opt-out category (`Choose Not To Warn`) that AO3 learned it needed after users tried to game a mandatory-warning system into spoiling their own plots. That's a real lesson, already paid for by someone else.

**Orphaning** — AO3's answer to "creator wants their name off it without deleting the work":

```
Work → transferred to Orphan_account → original attribution stripped →
  work remains archived, searchable, preserved → no longer editable by original author
```

This maps almost exactly onto TF's undesigned restriction/withdrawal/archive lifecycle. TF doesn't need to invent this from scratch; it needs three states (withdrawn-but-preserved, attribution-stripped-but-preserved, fully-deleted) and AO3 already field-tested which of those three actually gets requested in practice and why.

## The Improvement Spec

| TF Gap | AO3 Pattern to Borrow | Adaptation Needed |
|---|---|---|
| Capsule/path canon-clarity taxonomy drift | Freeform → wrangled → canonical tag pipeline | Steward plays wrangler role; smaller scale means no dedicated wrangler team needed, just a review queue |
| Undesigned restriction/withdrawal/archive lifecycle | Orphaning (preserve without attribution) | Add a middle state AO3 doesn't need: "returned-with-notes but preserved," since TF's model has an iteration loop AO3's doesn't |
| No CIE/PIE consent model | Fixed-enum rating/warning taxonomy + explicit opt-out category | Consent enum needs to cover *AI transformation type*, not content severity — genuinely new enum values, borrowed structure only |

# Spec 3: Patreon/Substack Monetization Layer (Tertiary, Deferred to Stage 8)

Both platforms solve the same problem the same way: a "campaign" or "publication" object gates content behind a subscription, Stripe (or Stripe-equivalent) handles billing, platform takes a cut. Current published cut percentages for either platform are the kind of number that changes without notice, so don't build a business model around a figure I haven't verified against their current terms today, confirm the live rate before it goes in a deck.

The structural lesson worth taking regardless of the exact number: neither platform's billable unit is a "world." It's a creator. TF's monetization model, whenever it gets built, needs the billable unit to be the *storyworld* (so a steward could theoretically run multiple monetized universes, or co-stewards could split revenue on one), which is a genuine product decision neither Patreon nor Substack had to make because neither supports multi-owner creative property. That's a real design fork, not a borrowed pattern, and it's explicitly Stage 8, so it doesn't need solving now. Flagging it here so it doesn't get accidentally decided by default when someone eventually reaches for Stripe Connect and copies the nearest tutorial.

---

**Bottom line for the decision memo:** ADR-0003 isn't really "GitHub-native vs. custom backend" as originally framed. It's "GitHub-native vs. a worse reimplementation of GitHub." The two genuine build items, voice-first capture and CIE/PIE consent, are the only pieces where no donor organ exists anywhere in the competitive set. Everything else on the current Postgres schema has a documented, batle-tested equivalent sitting in a platform TF is already pushing every commit to.
