*Prepared 2026-08-19 by Jamie Hill (OverKill Hill P3) for the Replit build agent working `github.com/OKHP3/telling-forward`.*

## 0. How to use this document

This is a build directive, not a design exploration. It sits on top of `AGENTS.md` (the procedural contract for how to work in this repo) and answers the question AGENTS.md leaves open: what to build next, and under what authority.

Read in this order:

1. `AGENTS.md` — how to work in this repo (safe change procedure, validation commands, content conventions).
2. This document — what's authorized to build, what's locked, what's off-limits.
3. `docs/decisions/open-questions.md` and `docs/adr/*` — background on why. Section 4 below supersedes the "Open" status on the specific items listed there. Everything else in those files stays as written.

If any instruction here conflicts with a "Do Not Build" item in Section 10, Section 10 wins. If you hit a decision point not covered in Section 4, stop and raise it. Don't infer a call that isn't written down.

## 1. Product vision

Telling Forward is a voice-first, agent-assisted collaborative storytelling platform. Mission, verbatim from `docs/MISSION.md`:

> "Authorship can be accessible without becoming anonymous, and collaboration can be open without making ownership unclear."

Product concept: open-canon collaborative fiction. An author opens a storyworld. Contributors extend it on permissioned paths. Readers can always tell the author's canon from a community alternate. Agents assist without taking authorship. Provenance stays visible. Canon stays separate from possibility. Every world needs a steward. Monetization is earned only after real traction, not built in up front.

This directive does not change the mission. It scopes what gets built toward it right now.

## 2. Current state (as of 2026-08-19)

Built and verified in code:

- Auth (register, login, logout, session, GitHub OAuth, account lockout, password reset, email verification)
- Core domain schema: `storyworlds`, `story_paths`, `contributions`, `proposals`, `editor_questions`, `stewards`, `contributors`, `provenance_records`
- Capsule CRUD against GitHub Issues (list/create/update/delete), with a tested authorization boundary (`capsule-boundary.test.ts`) confirming only `capsule:*`-labeled issues are touched
- `/transcribe` endpoint on OpenAI audio, with per-user rate limiting
- Manuscript ingestion pipeline (DOCX/EPUB/PDF to markdown to scenes to draft capsules), tested against a synthetic fixture only
- MCP server for the bring-your-own-AI tier, smoke-tested with a real MCP client
- Six frontend scaffolds (`web`, `reader`, `archive`, `broadsheet`, `scriptorium`, `signal-noise`) sharing one shadcn/Tailwind design system, plus `mobile` (Expo, no confirmed scope) and `mockup-sandbox` (not production)

Documented but not built: capsule promote/disrupt/invert business logic (OpenAPI stub only), any notification system, GitHub webhook sync, steward moderation tooling, the Concept Board UI, the Reader App, a restriction/withdrawal/archive lifecycle for proposals, per-action consent for AI-derivative work.

Authoritative status source: `docs/reviews/2026-08-19-dream-platform-equilibrium-review.md`. Its verdict, verbatim:

> "Approve with limits for controlled Stage 0 discovery and bounded Stage 1 design."

Explicitly not approved: real untrusted uploads, public contribution, derivative transformation of another person's material, commercial activity, rights-sensitive publication. No live deployment, legal review, security test, restoration drill, or user study has been run.

## 3. Build authorization scope

Everything in this directive stays inside the equilibrium review's approval boundary. That boundary is the hard edge of this phase of work, not a suggestion.

| Authorized now | Not authorized — do not build toward this yet |
|---|---|
| Single private pilot storyworld, owner-controlled | Public contribution from unknown users |
| Stage 0 decision/safety-rail work | Untrusted file uploads from anyone but the owner |
| Bounded Stage 1 build (Workbench, Storyworld Kit, Concept Board, rules-only ingestion, basic reader edition, export) | Derivative AI transforms (CIE/PIE) of another contributor's material without a working consent model |
| Design (not full build) of the consent ladder and moderation tooling | Commercial or monetization features |
| Internal testing against synthetic/owned content | Rights-sensitive publication of any kind |

If a task looks like it needs to cross into the right-hand column to be "done properly," stop and flag it instead of building it partially. Partial builds of out-of-scope features are worse than not starting them.

## 5. Domain model directive

Build against the existing schema; extend it where this directive calls for new state. Do not introduce parallel or duplicate tables for concepts that already exist.

**Existing (keep as-is):**

- `storyworlds` — one row per GitHub repo/storyworld
- `story_paths` — one row per branch; states `personal`, `open`, `proposed`, `published-alternate`
- `contributions` — one row per commit ("saved moment")
- `proposals` — one row per PR ("story submission"); six-state machine per Section 4
- `editor_questions` — steward-facing review prompts
- `stewards` — governance role per storyworld
- `contributors` — contributor identity, scoped per Section 4 decision on 15.2
- `provenance_records` — durable ledger tying an accepted canon commit to contributors and deciding steward

**New for this phase:**

- **Proposal lifecycle extension**: add `restriction`, `withdrawal`, and `archive` states/fields to the proposal model. Currently canon-vs-alternate is the only outcome pair; the equilibrium review flags this as not covering real review outcomes (a steward rejecting, a contributor withdrawing, a piece being archived without a canon/alternate verdict). This is required before Stage 3, design it now.
- **Consent record** (design only, per 15.14): a table or record shape capturing per-action consent for AI-assisted operations, keyed to contributor + action type (transcription, agent-shaped draft, CIE, PIE). Do not implement enforcement yet — produce the schema and a decision memo on where it plugs into the existing flow.
- **Term/motif ledger** (per ADR-0006, now unblocked by the 15.12 decision): steward-facing ledger of canon terms and motifs, backed by capsule Issues, not a new source of truth.

**Explicitly not a new table:** capsules. They stay as GitHub Issues per the locked decision above. If Concept Board work seems to need a capsules table, that's a sign the requirement needs to route through GitHub Issues/Projects instead, not a reason to add one.

## 6. Architecture directive

- Keep the pnpm monorepo layout: `lib/` for shared packages, `artifacts/` for deployable apps, `.agents/` for repo-local skills, `scripts/` for Replit/git tooling.
- Stack stays as documented in `AGENTS.md`/`replit.md`: Node 24, TypeScript 5.9, Express 5, Postgres + Drizzle, Zod v4 + drizzle-zod, Orval codegen from `lib/api-spec/openapi.yaml`, esbuild for the CJS bundle, Replit autoscale deployment.
- GitHub integration: Octokit-based today via PAT; migrate to a GitHub App per the Section 4 decision on 15.6. Every domain table that mirrors GitHub state (SHA, PR number, branch ref) keeps doing so — Postgres is a cache, treat it as rebuildable from GitHub at any time. Do not add state to Postgres that can't be reconstructed from GitHub.
- "GitHub holds / Replit executes": GitHub is the durable record; Replit/the API server is the interface and orchestration layer. When in doubt about where a piece of state belongs, it belongs in GitHub unless there's a specific reason (rate limits, query performance, session/auth state) to cache it in Postgres.
- Auto-push stays on. Every commit is effectively public immediately — do not treat any commit as a safe place to stash secrets, drafts of unresolved decisions, or anything not meant for `github.com/OKHP3/telling-forward`.

## 7. Feature build list — this phase (Stage 0 + bounded Stage 1)

Build in this order. Each item lists its acceptance criteria. Don't start an item whose prerequisites aren't marked done.

**7.1 Storyworld Kit template repo**
Build a GitHub template repository that, when used, produces a correctly-structured storyworld repo (branch conventions, capsule label taxonomy, a starter `README`/mission file for the storyworld itself).
*Done when:* creating a new repo from the template and pointing the API server at it produces a working `storyworlds` row with no manual DB patching.

**7.2 Concept Board UI**
Per UI vision brief v3/v4: a non-linear, corkboard-style capture surface inside the Author App, rendering capsules (GitHub Issues) via a GitHub Project board. Two actions: **Disrupt** (prose-level) and **Invert** (concept-level), per the CME/CIE lineage documented in v4. Wire to the already-built capsule CRUD endpoints; do not duplicate that logic client-side.
*Done when:* a capsule created, edited, or deleted in the Concept Board round-trips correctly to the GitHub Issue and back, honoring the existing `capsule:*` label boundary test.

**7.3 Capsule promote/disrupt/invert backend logic**
The OpenAPI spec already stubs `/storyworlds/{id}/capsules/{capsuleId}/promote`, `/disrupt`, `/invert`. Implement the actual logic behind them (promote = capsule to scene; disrupt/invert = the two Concept Board actions from 7.2).
*Done when:* each endpoint has real behavior, matching test coverage in the same style as `capsule-boundary.test.ts`.

**7.4 Rules-only ingestion hardening (Tier 0)**
The manuscript ingestion pipeline works against a synthetic fixture. Harden it against real (owned) manuscript content: at least one real DOCX, one real EPUB, one real PDF, run end to end through conversion, segmentation, and capsule extraction.
*Done when:* three real-format documents produce sane scenes/capsules with no manual cleanup required, and failure modes (malformed file, unsupported format) fail gracefully with a clear error, not a crash.

**7.5 CME (Concept Maturation Engine) review flow**
A steward-facing review step for capsules moving through maturation, distinct from the existing proposal review flow (proposals are for prose/PRs; CME is for concept-level capsule maturity).
*Done when:* a steward can see a capsule's maturation state and move it forward, with the transition recorded in a way an audit trail could reconstruct.

**7.6 Basic reader edition**
Read-only view of the pilot storyworld's accepted canon, no contribution surface. This is the minimum viable version of the Reader App from UI vision brief v2 — pick one of the five starter themes, don't build all five yet.
*Done when:* a reader can open the pilot storyworld and read its canon content in the chosen theme, with correct attribution per `docs/adr/0001`'s vocabulary table (no raw Git terms on the reader-facing surface).

**7.7 Export / portability — actually test it**
The equilibrium review flags export as "Blocked — never tested." Pick the export path that already exists or is closest to existing, and run it for real against the pilot storyworld's content.
*Done when:* a full export of the pilot storyworld's content can be produced and re-imported (or at minimum, opened and verified readable) in a clean environment, closing one of the equilibrium review's seven required gates.

**7.8 Proposal lifecycle extension**
Implement the schema/logic from Section 5's "new for this phase" item: restriction, withdrawal, archive states on proposals.
*Done when:* a steward can restrict, and a contributor can withdraw, a proposal without forcing it through the canon/alternate binary, closing another equilibrium review gate.

**7.9 GitHub App migration**
Per Section 4's 15.6 decision.
*Done when:* the API server authenticates to GitHub via a scoped GitHub App installation instead of a personal access token, with the PAT path removed, not just deprecated.

**7.10 Consent ladder + moderation tooling — design only**
Per Section 5. Produce a written spec and schema; do not build enforcement UI.
*Done when:* there's a reviewable design doc and a draft schema, in the same rigor as the existing ADRs, ready to be picked up as a Stage 2/3 build item.

**7.11 Notification system — contributor-facing subset only**
Per ADR-0002's two-tier model: build the plain-language, five-state contributor inbox. Do not build the full technical maintainer/agent stream yet; that's lower priority while there's a single owner-operator.
*Done when:* a contributor action (proposal submitted, returned with notes, accepted) produces a visible, plain-language notification.

## 9. Non-functional requirements

- **Testing**: extend the existing Vitest suite (`auth-lockout`, `body-size-limits`, `capsule-boundary`, `transcribe-ratelimit`) with coverage for every new endpoint and state transition added in Section 7. No feature in Section 7 ships without a test in the same style as what's already there.
- **Security**: the untrusted-upload boundary is explicitly not authorized yet (Section 3). Don't build toward it. Do run a restore drill in a clean environment as part of 7.7 (export) — this closes one of the equilibrium review's required gates directly.
- **Cost controls**: any AI usage (transcription, future agent-shaped drafts) stays behind the existing per-user rate limiting pattern established in `transcribe-ratelimit`. Extend that pattern, don't invent a new one.
- **Validation commands**: run `pnpm run typecheck` and `pnpm run build` before any handoff, per `AGENTS.md`. No exceptions for "small" changes.
- **Change hygiene**: every commit auto-pushes and is effectively public (Section 6). Keep commits scoped to one Section 7 item at a time where practical, to keep the audit trail legible.

## 10. Do not build — hard stops

Do not build, or build toward, any of the following in this phase, regardless of how small a step it seems:

- Any surface that accepts contributions, uploads, or content from anyone other than Jamie (the owner) or the single pilot storyworld's designated internal testers
- Any storage or processing path for a contributor's unpublished third-party fiction without confirmed rights (per `CONTENT-LICENSE.md` and `AGENTS.md`'s scope boundary)
- CIE/PIE derivative-transform execution against another person's material — the consent model has to exist and be reviewed first (7.10 is design-only for a reason)
- Monetization, payment, royalty, or adaptation-rights promises of any kind to any contributor
- A code license decision beyond the Section 4 placeholder (proprietary/all-rights-reserved) — do not switch to a permissive license without a separate explicit decision from Jamie
- Any credential, token, or personal machine path committed to a tracked file — the `GITHUB_PAT` (and its GitHub App replacement, once 7.9 lands) stay out of git config, files, and process arguments, full stop

## 11. Definition of done for this phase (exit criteria)

This phase is complete, and Stage 2 work can be proposed, when all of the following are true. These map directly to the equilibrium review's seven required gates:

1. All Section 4 decisions are propagated into `docs/decisions/open-questions.md` (marked Decided) and `AGENTS.md` (gaps section updated).
2. A capability/traceability inventory exists mapping what's built against what's documented (this directive plus the 2026-08-19 review together mostly satisfy this — confirm it's current).
3. The restriction/withdrawal/archive lifecycle (7.8) is built and tested.
4. Export/portability (7.7) has been tested for real, including a clean-environment restore.
5. The consent ladder design (7.10) exists and has been reviewed, even though enforcement isn't built yet.
6. The GitHub App migration (7.9) is complete; PAT auth is removed, not just deprecated.
7. Moderation tooling design (7.10) exists as a prerequisite for any future Stage 3 public-contribution work.

Until all seven are true, do not treat this project as ready for anything beyond the single private pilot storyworld.
