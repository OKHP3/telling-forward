# Telling Forward: Stage 0 and Bounded Stage 1 Product Directive

You are working in the Telling Forward repository, an early prototype for a voice-first, agent-assisted collaborative storytelling platform.

Your job is not to build the entire dream platform at once. Build and validate the smallest trustworthy foundation for an author-led, invite-only pilot storyworld.

Treat this directive as a product and engineering contract.

## Product intent

Telling Forward helps people turn story ideas, memories, characters, and possibilities into attributable, readable work without requiring them to understand GitHub.

The intended experience is:

- A worldbuilder can create and organize a private storyworld.
- A worldbuilder can capture lightweight concepts called capsules.
- A worldbuilder can deliberately shape a capsule into an editable scene draft.
- A reader can eventually read an approved story path and understand whether it is canon or an alternate continuity.
- GitHub remains the durable record of story history, while the application provides a humane interface over the technical machinery.

The platform must preserve human creative control. Agents may assist, organize, draft, and flag concerns. They do not become authors, silently publish work, decide canon, or override a contributor’s rights.

## Operating posture

This is an early, actively evolving prototype.

Do not claim that any feature is deployed, operational, secure in production, legally approved, or ready for public contributors unless you directly verify that state in this workspace and its configured environment.

Use these evidence labels in planning notes, code comments when relevant, and handoff reports:

- **Confirmed:** directly supported by current source or an executed check.
- **Proposed:** recommended future work, not established behavior.
- **Open:** requires an owner decision.
- **Unknown:** not verified in the current session.

Do not convert Open or Unknown into implementation assumptions.

## Scope for this delivery

Deliver the foundation for a private Writer’s Workbench and one safe storyworld flow. Do not broaden into public community, monetization, or rights-sensitive automation.

The intended pilot is:

> An author-led, invite-only storyworld using only synthetic or demonstrably owned, non-sensitive material.

The pilot should make it possible to prove a simple journey:

1. An authorized worldbuilder opens an existing private storyworld.
2. They create, view, edit, and archive lightweight capsules.
3. They can review capsule provenance and status without confusing technical language.
4. They can deliberately request an editable scene draft from a capsule only where configured AI assistance is permitted.
5. No draft becomes published prose, canon, or an alternate path automatically.
6. The work remains attributable and recoverable.

## Hard exclusions

Do not build or enable any of the following in this delivery:

- Public contribution or open registration for a real community.
- Real untrusted manuscript uploads.
- Processing of private, third-party, or rights-uncertain fiction.
- Commercial rights, royalties, credits as economic value, payments, or adaptation programs.
- Automatic canon acceptance.
- Automatic publication.
- CIE, PIE, Disrupt, Invert, translation, or other derivative transformations of another person’s material.
- A claim that generic AI consent authorizes derivative generation.
- A claim that a local build or source inspection proves a live Replit deployment.
- A production designation for any client package until open question 15.3 is decided.

Use synthetic fixtures only for automated tests and demonstrations.

## Product vocabulary

Contributor-facing language must use:

- Storyworld
- Story seed
- Story path
- Saved moment
- Story submission
- Editor question
- Accepted into canon
- Published alternate path

Keep GitHub’s terms backstage. Code may use Git terminology where necessary.

Do not conflate these separate axes:

1. Ownership and permission type:
   - Personal work
   - Open path
   - Proposed canon
   - Published alternate path

2. Submission review status:
   - Current implementation and requirements use Draft, Submitted, Under review, Returned with notes, Accepted into canon, and Published alternate path.

There is a recorded four-state versus six-state discrepancy. Do not silently “fix” it. Surface it as an owner decision and keep any new work compatible with the currently implemented six-state schema unless the owner directs otherwise.

## First implementation priorities

### Priority 1: Establish a current capability and traceability baseline

Create or update a concise, dated capability matrix that maps each Stage 0 and Stage 1 requirement to:

- Current status: implemented in checkout, tested, deployed, accepted, deferred, not started, or blocked.
- Relevant source paths.
- Durable records created or changed.
- Owner decision or prerequisite.
- Acceptance evidence.
- Explicit exclusions.

This is not governance for its own sake. It must make clear what the prototype can do today versus what the roadmap proposes.

### Priority 2: Normalize the capsule contract

There is a material mismatch to resolve before capsule work can be trusted:

- The API Concept Board routes recognize GitHub Issues labeled `capsule:*`, such as `capsule:character`.
- The manuscript-ingestion workflow and MCP server create or read Issues labeled `capsule` plus `kind:*`.

As written, capsules created by the workflow or MCP tier may not appear in the Concept Board.

First produce a short compatibility decision note identifying every affected source path. Then implement one canonical capsule Issue contract for the bounded pilot, including:

- Exactly one canonical capsule type label.
- Optional role label.
- Optional maturity label.
- Stable title and body semantics.
- Clear handling for types that cannot yet be represented without loss.
- A migration or compatibility plan that is safe for existing Issues and does not mutate real repositories without explicit approval.

Add focused tests proving that capsules created through the API, MCP server, and ingestion adapter are all visible to the same Concept Board query.

### Priority 3: Make authentication behavior coherent

Current source combines Clerk identity, legacy email/password routes, Express sessions, and optional GitHub account linking.

Do not choose a permanent contributor identity model without owner direction. Open question 15.2 remains authoritative.

However, do identify and test the current behavior of:

- Sign-in.
- Current-user lookup.
- Protected steward routes.
- Capsule routes.
- Transcription authorization.

If legacy session login cannot reach routes guarded by Clerk identity, document that as a current limitation. Do not present legacy email/password authentication as supported for protected product flows until it passes an end-to-end test.

### Priority 4: Keep AI assistance bounded and consent-aware

The private pilot may support an owner-operated scene-draft assist only if all of the following are true:

- The capsule belongs to the authorized worldbuilder.
- The source material is synthetic or demonstrably owned.
- The user can inspect and edit the result.
- The result is clearly marked as agent-assisted.
- The result is not auto-saved as canon, submitted, published, or treated as a contributor’s final expression.
- Missing model configuration produces a clear manual fallback.

Do not enable Disrupt or Invert for real user material. Their consent, lineage, opt-out, and revocation model is still Open.

### Priority 5: Produce one readable private path

Do not build a broad discovery network. Create or stabilize one bounded reader path for the pilot that can show:

- Storyworld title and seed.
- A readable selected scene or synthetic fixture.
- Attribution.
- Canon or alternate status.
- Agent-assistance disclosure when applicable.
- A plain-language explanation of what the reader is seeing.

Do not invent creative source material. Use clearly labelled synthetic fixture text where a demonstration is necessary.

## Data and integration rules

GitHub is intended to remain the durable system of record for story history. PostgreSQL may provide an application cache and query layer, but it must not become the only place where essential provenance or rights information exists.

For any new durable record, define:

- Its canonical location.
- Its identifier.
- Its relationship to GitHub-native identifiers.
- Its visibility.
- Who can change it.
- How it is recovered, restricted, withdrawn, or exported.
- Whether it contains personal, creative, or rights-sensitive content.

Do not add a real-upload path until the untrusted-upload contract is approved and tested. A private upload is still a security and confidentiality boundary.

Do not rely solely on webhooks. Preserve the existing reconciliation direction and document whether a scheduled reconciliation mechanism remains unimplemented.

## Security and privacy rules

Preserve and verify existing protections where they apply:

- Signed GitHub webhook verification.
- Production CORS allowlisting.
- Secure HTTP-only session cookies.
- Body-size limits.
- Database-backed transcription limits.
- Login lockout.
- Steward authorization checks.
- No tokens in source, Git config, logs, process arguments, or client bundles.

Never add secrets to tracked files. Reference environment-variable names only.

Treat a successful local check as local evidence only. It does not prove deployment, secret configuration, GitHub permissions, Clerk behavior, email delivery, OpenAI access, or production security.

## UX direction

The Author App should feel like a calm editorial workbench, not a project-management tool or a Git client.

A capsule should be cheap to create:

- Name
- Type
- Optional role
- Optional one-line note

More detail should be available without forcing a form-heavy workflow.

Preserve the distinction between the Author App and Reader App. Do not merge every existing visual package into one surface. Keep `artifacts/mockup-sandbox` for design exploration. Treat `artifacts/web` as the current integration candidate only, not as an owner-approved production designation.

If exploring a major visual change, extract the actual current component into the sandbox first. Keep design variants separate from production wiring. Do not graduate a mockup without a clearly approved variant.

## Required acceptance evidence

Before handing work back, provide:

1. A concise capability/traceability matrix.
2. Exact changed files and why each changed.
3. A capsule-contract compatibility report.
4. A list of owner decisions still required.
5. Focused automated tests for the capsule contract and authentication boundaries.
6. Typecheck and build results, or exact blockers if they do not run.
7. A clean `git diff --check`.
8. A statement distinguishing:
   - Implemented in checkout
   - Tested locally
   - Deployed
   - Owner-approved
   - Still proposed or unknown

The core success test is not “all screens exist.”

The core success test is:

> One worldbuilder can use clearly owned or synthetic material to create and review at least five private capsules, deliberately shape one into an editable draft, publish no work by accident, and understand where the record and permissions live.

## Decision gates that stop further work

Pause and request owner direction before work that depends on:

- Repository-per-storyworld versus multiple worlds per repository.
- Contributor identity model.
- GitHub App versus PAT for platform integration.
- Production web-client designation.
- Code license.
- Creative-source content location and public/private boundary.
- Four-state versus six-state submission workflow.
- Action-specific consent for derivative transformations.
- Moderation requirements for public contribution.

If a request crosses one of these gates, do not guess. State the exact decision, affected records, and the smallest viable options.
